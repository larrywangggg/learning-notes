## 一、依赖包说明

一套完全本地化的 RAG 系统常用依赖（基于 LlamaIndex）。

### LlamaIndex 核心与组件

| 包 | 作用 |
|----|------|
| `llama-index-core` | 核心库。提供数据索引、检索、查询引擎等基础框架，把「文档 → 索引 → 检索 → 喂给大模型回答」整个流程串起来，是整套系统的"骨架"。 |
| `llama-index-readers-file` | 文件读取器。把本地文件（PDF、Word、txt、Markdown 等）加载并解析成 LlamaIndex 能处理的文档对象。 |
| `llama-index-llms-ollama` | 连接 Ollama 的适配器。让 LlamaIndex 调用本地 Ollama 上的模型生成回答，无需联网、不花 API 费用。 |
| `llama-index-embeddings-huggingface` | 嵌入（Embedding）模型适配器。把文本转换成向量用于语义检索，使用 HuggingFace 上的本地嵌入模型。 |
| `llama-index-vector-stores-chroma` | 让 LlamaIndex 把向量存到 Chroma 数据库的适配器（连接层）。 |

### 底层依赖

| 包 | 作用 |
|----|------|
| `chromadb` | 开源向量数据库。存储和检索文本向量，支持"找出语义最相近的内容"这类查询，是检索环节的实际存储引擎。 |
| `sentence-transformers` | 生成句子嵌入向量的底层库。`llama-index-embeddings-huggingface` 通常在背后调用它来真正运行嵌入模型。 |

### 整体协作流程

```
文件(readers-file) → 切分文本 → 嵌入(sentence-transformers / embeddings-huggingface)
    → 存入向量库(chromadb / vector-stores-chroma)
    → 提问时检索相关片段 → 交给本地大模型(llms-ollama) → 生成答案
                  ↑ 全程由 llama-index-core 调度
```

> **特点**：这套组合完全本地化运行（Ollama + HuggingFace + Chroma 都在本机），适合对数据隐私敏感、不想依赖 OpenAI 等云端 API 的场景。

## 二、Llama / LlamaIndex / Ollama 的区别

三个名字都带 "llama"（羊驼🦙）纯属巧合 + 行业梗，背后是三个不同的东西。

### 1. LLaMA — Meta 的大语言模型

LLaMA（Large Language Model Meta AI）是 Meta 开发的一系列**开源大语言模型**，类似 GPT，但开源、可免费本地部署。

- 版本演进：LLaMA 1 → Llama 2 → Llama 3 / 3.1 / 3.2 …
- 特点：性能强且权重公开，是开源 AI 社区最主流的基础模型之一，很多其他模型基于它微调。

### 2. LlamaIndex — 数据 / RAG 开发框架

`requirements.txt` 里的 `llama-index-*` 指的是 LlamaIndex，名字里也有 "llama" 但和 Meta 的模型不是一回事。

- 它是一个**数据框架**，用来把自己的文档接入大模型做 RAG。
- 它本身不是模型，而是"调度工具"——可以连接各种模型（Llama、GPT、Qwen 等）。

### 3. Ollama — 本地模型运行工具

`llama-index-llms-ollama` 里的 Ollama 是一个**本地运行大模型的软件**，让你在自己电脑上一键跑 Llama、Qwen、Mistral 等模型。

### 一句话区分

| 名字 | 是什么 | 角色 |
|------|--------|------|
| LLaMA / Llama | Meta 的开源大模型 | 真正"会思考"的模型 |
| LlamaIndex | 数据 / RAG 框架 | 调度、连接文档和模型 |
| Ollama | 本地模型运行工具 | 在你电脑上跑模型的"引擎" |

## 三、RAG 与 Agent 的关系

> **一句话**：RAG 是"让模型查资料"的技术；Agent 是"让模型自主做事"的框架。Agent 可以使用 RAG，但 RAG 不一定需要 Agent。

### 各自定义

**RAG（检索增强生成）**
- 解决的问题：大模型不知道你的私有数据、最新数据，容易"瞎编"。
- 做法：提问时先去知识库检索相关资料，把资料塞进提示词，再让模型基于这些资料生成回答。
- 本质：给模型"开卷考试"，临时喂参考资料。

**Agent（智能体）**
- 解决的问题：复杂任务需要多步骤、自主决策、调用工具，而不是一问一答。
- 做法：模型作为"大脑"，自己规划步骤、选择工具、观察结果、再决定下一步，循环执行直到完成任务。
- 本质：让模型"会做事"，能主动调用各种工具（搜索、计算、写文件、调 API…）。

### 两者关系

RAG 只是 Agent 的一种工具：

```
Agent（决策大脑，能用多种工具）
┌──────────────────────────────┐
│  工具1：RAG 检索知识库          │  ← RAG 只是 Agent 的一种工具
│  工具2：网页搜索               │
│  工具3：执行代码               │
│  工具4：调用外部 API           │
└──────────────────────────────┘
```

### 关键区别：决策权在谁手里

| | 普通 RAG | Agent + RAG |
|---|----------|-------------|
| 检索时机 | 固定：每次必检索一次 | 自主：模型判断要不要检索、检索几次 |
| 流程 | 检索 → 生成，一条直线 | 思考 → 行动 → 观察 → 再思考，循环 |
| 能否换工具 | 不能，只会查知识库 | 能，按需选不同工具 |

### 三种典型组合

1. **纯 RAG（无 Agent）** — 最常见。LlamaIndex 项目即属此类：问题进来 → 查 Chroma 向量库 → 把结果给模型 → 出答案。流程是写死的。
2. **Agentic RAG（Agent 驱动的 RAG）** — 模型自己决定：要不要查库？查哪个库？查到的不够好要不要换关键词再查？比纯 RAG 更聪明、更灵活。
3. **纯 Agent（不一定用 RAG）** — 比如会订机票、改代码的 Agent，可能不需要知识库检索，而是调用其他工具。

## 四、纯 RAG 需要哪些模型

**需要。** 纯 RAG 也必须有大模型——通常需要**两个**。RAG 里的 "G"（Generation 生成）就靠模型完成，没有模型就只能检索出一堆资料，没法生成回答。

### 需要的两个模型

| 模型类型 | 作用 | 项目里对应 |
|----------|------|------------|
| 生成模型（LLM） | 读检索到的资料，写出最终答案 | Ollama 上拉的 Llama / Qwen 等 |
| 嵌入模型（Embedding） | 把文字转成向量，用于检索 | HuggingFace 的 sentence-transformers 模型 |

两个都得"拉"（下载到本地）才能用。

### 对应到 requirements.txt

```
llama-index-llms-ollama            → 用 Ollama 跑生成模型，需要先 ollama pull <模型>
llama-index-embeddings-huggingface → 用嵌入模型，首次运行会自动从 HuggingFace 下载
```

拉生成模型示例：

```bash
# 拉生成模型（举例）
ollama pull llama3.2
# 或中文友好的
ollama pull qwen2.5
```

> 嵌入模型一般不用手动拉——代码里指定名字（如 `BAAI/bge-small-zh`）后，第一次运行 `sentence-transformers` 会自动下载缓存到本地。

### 能不能不拉模型？

可以，但要换思路：用**云端 API** 代替本地模型。比如把生成模型换成 Claude / OpenAI 的 API（改用 `llama-index-llms-anthropic` 之类的包），就不用本地拉几个 GB 的模型，但需要联网 + API Key + 按量付费。

当前这套配置走的是**纯本地路线**，因此需要拉模型。
