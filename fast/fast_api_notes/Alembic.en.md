# Alembic Quick Notes (EN)

Goal: understand Alembic’s role in FastAPI/SQLAlchemy projects, its workflow, and key files.

---

## 1. What Alembic Is
One‑liner: **Alembic is SQLAlchemy’s official schema versioning tool.**  
It records each schema change as a migration script, like a “Git commit for the database schema.”

---

## 2. Why You Must Use Alembic
Without Alembic:
- dev/test/prod schemas drift
- no trace of how tables evolved
- manual changes are hard to roll back

Example (messy reality without Alembic):
- Dev A manually adds `users.nickname`
- Dev B adds `users.age` in the test DB
- Production is still on the old schema
Result:
- same code breaks in different environments
- no clear upgrade order
- no safe rollback path

With Alembic you get:
- **traceable versions** (revision / down_revision)
- **consistent environments** (upgrade everywhere)
- **safe rollback** (downgrade)

---

## 3. The Three Core Roles
1. **SQLAlchemy Models**: your “ideal” schema (ORM models)
2. **Database**: the “real” schema (actual tables in Postgres)
3. **Migration Scripts**: the bridge that moves reality to the ideal

Example (model change):
```python
class User(Base):
    __tablename__ = "users"
    id = mapped_column(Integer, primary_key=True)
    email = mapped_column(String, unique=True, nullable=False)
    is_active = mapped_column(Boolean, default=True)  # new column
```

---

## 4. Key Files and Folders
```
alembic/
├─ env.py
├─ script.py.mako
└─ versions/
   ├─ xxxx_init.py
   └─ yyyy_create_jobs_and_results.py
```

- `alembic/versions/*.py`: migration scripts with `upgrade()` / `downgrade()`
- `alembic/env.py`: loads `DATABASE_URL` and `Base.metadata`
- `alembic_version` table: stores current DB revision

Example (migration snippet):
```python
def upgrade():
    op.add_column("users", sa.Column("is_active", sa.Boolean(), nullable=True))

def downgrade():
    op.drop_column("users", "is_active")
```

Example (`env.py` key line):
```python
from app.db import Base
target_metadata = Base.metadata
```

---

## 5. Standard Workflow (Most Common)
1. **Edit models** (SQLAlchemy Models)
2. **Generate migration**  
   `alembic revision --autogenerate -m "add xxx"`
3. **Apply migration**  
   `alembic upgrade head`

Rollback:
`alembic downgrade -1`

Example commands:
```bash
alembic revision --autogenerate -m "add users.is_active"
alembic upgrade head
```

Mental model (timeline):
```
models.py
↓
alembic revision (generate script)
↓
alembic upgrade (run script)
↓
database schema changes
↓
alembic_version records current revision
```

---

## 6. What Autogenerate Does
`--autogenerate` will:
- read `Base.metadata`
- compare with the current database schema
- generate a migration file  
Note: **it only writes files, it does not modify the DB**.

Example output:
```
INFO  [alembic.autogenerate.compare] Detected added column 'users.is_active'
```

---

## 7. Common Pitfalls
- always generate + apply migrations after model changes
- review autogenerated scripts before applying
- in production, only use `upgrade`, never manual edits
- `alembic_version` stores a single current revision

---

## One‑Sentence Summary
Alembic turns schema changes into a versioned, repeatable, and reversible workflow, which is foundational for long‑term backend maintenance.
