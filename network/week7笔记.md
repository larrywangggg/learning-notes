## 第一部分：IoT 与 MQTT

### 1. 传输协议选择的背景

应用程序设计时必须选择传输层协议：

- **TCP**：大文件传输、长会话、需要可靠性（如 HTTP）
- **UDP**：短消息、低延迟、简单请求/响应（如 RTP）

这些协议在"正常尺寸"的计算机上运行没问题，但当设备变得极小时（IoT），一切都需要重新考虑。

### 2. 什么是 IoT（Internet of Things）

IoT 的核心思路：把任何设备连接到互联网。

**设备规模从大到小：**

- **大型设备**：智能冰箱（能扫描食材、透明屏幕）、洗衣机（完成提醒、能耗监控）、可远程控制的插线板（每个插口独立控制，支持定时/触发）、变色灯泡（内置 CPU + WiFi）
- **中型设备**：Raspberry Pi（通用计算机，有 OS，能并行运行多个程序）、Arduino（单程序微控制器）
- **小型设备**：ESP32（带摄像头、SD 卡槽，可以做 AI）— 录播中 Markus 带了实物展示
- **微型设备**：比硬币还小的芯片，可以放在指尖上、散布在田野中（smart dust）、注入血液中

> **录播补充**：Markus 提到他带了多种设备到课堂展示。ESP32-S3 比老款 ESP32 更小更强，配合子板（daughter board）就能做成完整的安防摄像头。他个人用来做野生动物追踪相机：一个被动红外传感器做触发器，ESP32 负责拍摄和 WiFi 网状传输。

**Smart Dust 概念**：微型芯片散布在地面上，通过压力传感检测人员通行。每个人的步态（gait）像指纹一样独特，可以区分个体。

**IoT 应用场景（M2M，大规模）：**

- 工业设备预测性维护（温度、压力、噪音异常检测）
- 农业（从每个农场一个传感器 → 每棵植物一个传感器，几美元一个）
- 水质监测（塔斯马尼亚牡蛎养殖场案例：上游农场化学品泄漏通过传感器数据回溯发现）
- 交通流量、V2V（车对车）和 V2I（车对基础设施）通信
- 军事应用

### 3. "Phone Home" 问题

几乎所有 IoT 设备都依赖"回家打电话"机制：

- 设备在 NAT 后面 → 需要动态 DNS → 厂商运行中心服务器
- 每个品牌都有自己的 App 和私有协议
- 你的手机上会有几十个 App 来控制不同设备

**风险案例（录播中大量展开）：**

| 案例 | 问题 |
|------|------|
| Insteon 倒闭 | 服务器关停，用户无法控制灯泡和插线板 |
| Nike 自动系带鞋 | 服务器宕机 → 无法检查固件更新 → 鞋子"变砖" |
| 欧洲豪车 RFID 解锁 | 展厅是法拉第笼，无法连接服务器，打不开车门 |
| Ring 门铃摄像头 | CEO 向警方出售用户摄像头数据访问权 |
| 智能婴儿床 | 被黑客入侵：扬声器音量无上限 + 摇动马达无限制 |
| 婴儿监视器 | 被黑客入侵，陌生人对着别人的婴儿说话 |
| 宠物喂食器 | COVID 期间技术人员无法进入机房 → 服务器宕机 → 宠物断粮 |
| Eight Sleep 智能床 | 和婴儿床一样的漏洞，可远程折叠用户 |
| 汽车 OTA 更新 | 更新时重置所有系统包括驻车制动，要求停在平地 |

### 4. IoT 为什么"不一样"？

五大挑战 + 一个隐含挑战：

1. **规模（Scale）**：设备数量可达数十亿。N 个设备 → N² 个关系。10 亿设备 × 1 byte/s = 10 Gbps 数据
2. **功耗（Power）**：设备越小越受限。能量收割技术：太阳能、动能、热能、RF
3. **网络（Networking）**：低功率 = 短距离 + 低频率发送。Mesh 网络、限制传输需求
4. **时效性（Timeliness）**：核反应堆 vs 室外温度，需求完全不同
5. **可靠性（Reliability）**：在需要的地方添加，保持轻量。状态变化 vs 持续报告
6. **灵活性（Flexibility）**：用途不可预测，需要支持任意应用

### 5. IoT 协议概览

| 协议 | 特点 |
|------|------|
| CoAP | 基于 HTTP/UDP，安全层太重，很少使用 |
| DDS | 基于 IP 多播 |
| Matter | 新兴智能家居标准，运行在 WiFi/Thread/Zigbee 等之上 |
| AMQP | 基于 Broker 的消息队列 |
| MQTT | 本课重点，基于 Broker 的 PubSub 模型 |

很多协议都使用 **PubSub（发布/订阅）** 模型，而非传统的 Client/Server 或 Broadcast。

### 6. PubSub 模型

核心思想：将数据的"发布"与"消费"分离。

- **发布者（传感器等）**：只管把数据推送给 Broker，不知道/不关心谁在听
- **Broker（中间人）**：接收数据，转发给所有订阅者，然后尽快删除
- **订阅者（消费者）**：向 Broker 注册兴趣，等待推送

关键点：发布者和订阅者之间没有直接连接。Broker 承担所有路由工作。两侧在 MQTT 文档中都被称为 "clients"。

### 7. MQTT 协议详解

**基本信息：**

- 原名 Message-Queueing Telemetry Transport（IBM 1990s）
- 现已不再排队（mostly），也不限于遥测
- v3.1 运行在 TCP 上；v5（2018）开始支持 UDP、Zigbee 等（MQTT-SN）
- 由 OASIS（非 IETF）标准化
- 本质上是一个尽快删除数据的 key/value 数据库

#### 7.1 Topic 结构

Topic 是分层的 key：`topic/subtopic/sub-sub-topic/...`

示例：
```
Sensors/Paddock-A/Moisture/Sensor-1 = 93%
Sensors/Paddock-B/Temperature/Sensor-3 = 28C
PizzaPreferences/HouseMate/Malcolm = "vegetarian, but no olives"
```

Value 可以是：数字、字符串、文件、JSON 对象等。Topic 不需要预先创建，直接写入即可。

#### 7.2 订阅通配符

- **`#`**（放在最后）：匹配该级别及以下所有内容
  - `Sensors/#` → 所有传感器的所有数据
  - `Sensors/Paddock-A/#` → Paddock-A 下所有传感器
- **`+`**：替换单个层级
  - `Sensors/+/Moisture/+` → 所有位置的所有湿度传感器

> **录播补充（学生提问）**：`+` 只匹配一层，不会穿透到下面的子层。如果 Sensor-1 下面还有子层，`+` 不会匹配到，这时应该用 `#`。设计 topic 结构时要提前考虑消费者如何切片。

#### 7.3 $SYS/# — Broker 系统信息

- Broker 自己发布的系统状态信息，包含：版本、运行时间、客户端数量、消息统计、带宽统计等
- 字段不标准化（每个 broker 实现不同）、更新频率低（可能 60s 一次）
- 讽刺：用 MQTT 监控 MQTT broker 本身的健康状态并不靠谱——broker 出问题时就不会更新 `$SYS`

#### 7.4 MQTT 报文结构

非常紧凑，面向 bit 操作：

- **Header**：消息类型（4 bit）、DUP 标志、QoS（2 bit）、Retain 标志
- 可变长度头 + 可变长度载荷
- 只有 16 种消息类型

**主要消息：**

- `CONNECT` / `DISCONNECT`（+ ACK）
- `PINGREQ` / `PINGRESP`（应用层心跳，不是 ICMP）
- `PUBLISH`（双向使用：source→broker 和 broker→subscriber）
- `SUBSCRIBE` / `UNSUBSCRIBE`（+ ACK）
- `PUBACK` / `PUBREC` / `PUBREL` / `PUBCOMP`（QoS 相关）

#### 7.5 QoS（Quality of Service）

三个级别，开销递增：

**QoS 0 — Fire and Forget**
- 发送后立即删除，不确认
- `Client → PUBLISH → Broker`，完事

**QoS 1 — At Least Once**
- 保证送达，但可能重复
- `Client → PUBLISH → Broker → PUBACK → Client`
- 如果 PUBACK 丢失，Client 重发（带 DUP 标志）

**QoS 2 — Exactly Once**
- 保证送达，保证不重复，4 步握手
- `Client → PUBLISH → Broker → PUBREC → Client → PUBREL → Broker → PUBCOMP → Client`
- `PUBREL` 是"允许你现在分发给所有订阅者"的信号
- 代价最大：能量、时间、存储

**QoS 可以混合使用：**
- 发布端和订阅端可以使用不同的 QoS 级别
- 例如：传感器用 QoS 0 发布（省电），核反应堆控制系统用 QoS 2 订阅（保证送达）
- 或者：传感器用 QoS 2 确保 broker 收到，boss 的手机用 QoS 0 随便看看
- 注意：有些 broker 不支持混合模式

#### 7.6 Retain（保留消息）— Last Known Good

**问题**：门传感器一天才发一次状态变化，新订阅者加入时可能要等很久才能收到第一条消息。

**解决**：发布时设置 Retain 标志。Broker 会保留这条消息，新订阅者一连接就能收到最后一条保留消息。

- 保留消息在 broker 文件系统中持久化，重启后仍然存在
- 不会自动删除——必须显式写入空值才能清除

> **录播补充（学生提问）**：保留消息永远不会自动清除，要删除必须主动写入空值覆盖。对于门传感器，每次状态变化都会覆盖上一条保留消息，这种场景一般会用 QoS 2 来确保状态变化可靠写入。

#### 7.7 Last Will and Testament（遗嘱消息）

传感器在首次连接时预设一条"遗嘱"消息。当：

- Broker 在 KeepAlive 周期内未收到心跳，或
- TCP 连接断开但没有正常的 MQTT `DISCONNECT`

Broker 就认为连接丢失，发布预设的遗嘱消息通知所有订阅者。

示例遗嘱消息：`"Service temporarily down; contact x@y.com"`

#### 7.8 Clean Session vs Persistent Session

- **Clean Session（默认）**：连接时当作全新客户端，只收到 retained messages
- **Persistent Session**：要求 broker 记住你的所有订阅和未接收的消息（QoS 1/2）
  - 断线重连后，broker 会推送你错过的所有消息（burst）
  - 对 broker 压力很大——需要存储所有相关消息

### 8. MQTT 在智能家居中的应用

- **被动监控**：所有传感器（亮度、温度、湿度、运动等）发布到 MQTT → 绘制趋势图
- **主动控制**：控制设备（灯、暖气、窗帘、门锁）订阅命令 topic → 控制器（物理开关、App、语音助手）发布命令

**关键设计**：控制器不直接发布到被控设备，而是通过 broker 中转，软件层可以在中间添加逻辑。

**规则引擎和状态机：**

- **IFTTT / NodeRed**：简单的"如果 X 发生，则做 Y"触发器
- **Home Assistant / OpenHAB**：完整状态机，可以整合历史数据、天气预报、时间等多维度信息，构建复杂场景

> **录播补充**：Markus 展示了一个 RF 桥接器——连接 WiFi 接收 MQTT 命令，然后通过 433MHz RF 信号控制电视等不支持 MQTT 的设备。MQTT 不必端到端使用，可以做协议桥接。

### 9. IoT 安全问题

> "The S in IoT stands for Security"（IoT 中的 S 代表安全——但 IoT 没有 S）

**现实问题：**

- 固件 v1.0 → 十年不更新
- 默认管理员账号密码从不修改
- 标准化的管理 URL，可以 Google 搜到
- 云网关可能随厂商倒闭而消失
- 设备被攻陷 → 成为家庭网络的立足点 → 横向攻击

> **录播补充**：Philips 灯泡案例——第一个灯泡连上 WiFi 后，第二个灯泡会搜索同品牌灯泡并**明文**询问 WiFi 密码。攻击者可以伪装成同品牌灯泡获取你的家庭 WiFi 密码。

**MQTT 自身的安全机制：**

- 用户名/密码认证
- Client Identifier（最长 64KB）
- RBAC（基于角色的访问控制）
- X.509 证书
- 载荷签名和完整性校验
- 加密连接

### 10. 智能家居网络协议

**短距离协议：**

| 协议 | 特点 |
|------|------|
| WiFi | 高带宽，高功耗 |
| Bluetooth/BLE | 短距离，低功耗 |
| Zigbee | 更远距离，穿墙好，数十 kbps |
| Z-Wave | Zigbee 竞争者，完全私有 |
| Thread | 802.15.4 + IPv6 mesh，Google 等主导 |
| Matter | 上层应用协议，跑在 Thread/WiFi/BLE 上，Apple/Google/Amazon/Samsung/IKEA 联盟 |

**广域 IoT 网络：**

- **NB-IoT**：蜂窝网络（Telstra/Optus 提供），极远距离
- **LoRaWAN**：超低功耗，20km 距离，~10 kbps 共享带宽，发射器几十澳元
- **SigFox**：LoRaWAN 的私有版本

## 第二部分：P2P 与 DHT

### 1. Client/Server 模型的问题

| 问题 | 说明 |
|------|------|
| 中心化 | 依赖特定服务/提供商 |
| 脆弱 | 单点故障，攻击蜜罐 |
| 低效 | 一个服务器对多客户端 = 瓶颈 |
| 扩展成本高 | 更好的服务 = 更多服务器节点 |
| 缺乏隐私 | 通信路径上可以观察到你访问了什么 |

### 2. P2P 的理想特性

- **去中心化**：一群独立、平等的节点互利合作
- **鲁棒**：无单点故障
- **高效**：无瓶颈，优化数据传输
- **可扩展**：大量节点
- **自组织**：即插即用
- **匿名**：很难实现

### 3. P2P 性能优势

- **Client/Server**：1 个服务器 → N 个接收者 → 时间随 N 线性增长
- **P2P**：将文件分成 N 份放在 N 台机器上 → 聚合带宽 = N × 每个 peer 的带宽 → 时间几乎不随 N 增长（趋近常数）

**非对称带宽的利用：**

- 家庭宽带典型比例 100/20 Mbps（下行/上行 = 5:1）
- 从 1 个人只能获得 20 Mbps 上传速度
- 但从 5 个人各获得 20 Mbps = 100 Mbps，填满下行管道

**Bootstrap 问题**：Client/Server 你知道两端。P2P 你怎么找到其他 peer？

### 4. Napster（1999）

- 第一个"病毒式传播"的 P2P 应用，1 年内超过 1 亿用户
- 背景：MP3 压缩技术 + 拨号上网 + CD ripping
- **架构**：中央索引服务器 + 点对点文件传输
  1. 客户端索引本地音乐文件 → 上传到中央服务器
  2. 搜索时查询中央索引 → 返回拥有该文件的机器 IP
  3. 直接从该机器下载文件
- **优点**：简单，支持灵活搜索
- **致命缺点**：中央服务器 = 单点故障 + 法律攻击目标
- **历史影响**：被法院关停 → 催生了 iTunes → Spotify（从购买到租赁的转变）

> **录播补充**：Napster 的法律辩护策略是"我们只是帮助犯罪分子的无辜工具"，最终律师和法官不买账。但它证明了数字音乐有巨大市场。

### 5. Gnutella（2000）

- 第一代无结构/去中心化 P2P 协议
- **架构**：无中央服务器，查询靠洪泛（flooding）
  1. 向所有邻居发送查询
  2. 邻居递归转发
  3. 找到后回复给发起者
- **优点**：去中心化，高鲁棒性，灵活查询
- **缺点**：
  - 不可扩展，查询传播慢
  - 需要 TTL 限制查询传播范围
  - 超过一半的流量是查询流量（不是文件下载）
  - 容易被恶意节点干扰（音乐产业加入网络发起大量虚假查询和投毒内容）

### 6. BitTorrent（2001）

由 Bram Cohen 开发。设计目标：

1. **安全分片**：文件分成小块加密，持有部分碎片不会被追责
2. **利用非对称带宽**：从多个上传者同时下载
3. **公平激励**：游戏化机制（tit-for-tat 博弈），只有上传才能下载
4. **高效利用 TCP**：大量参数调优

#### 6.1 核心组件

- **Tracker**：中央目录（原始版本），只跟踪 peer 身份，不持有文件内容，只告诉你部分 peer（如 10-20 个）
- **.torrent 文件**：静态元数据，包含 Tracker 地址、文件信息、所有 piece 的索引和 SHA-1 哈希
- **Piece**：256KB 或 512KB 的文件块
- **Sub-piece**：16KB，用于 TCP 并行下载

#### 6.2 角色术语

- **Swarm**：所有参与的 peer
- **Seeder**：拥有完整文件的 peer（只上传）
- **Leecher**：正在下载的 peer（边下载边上传）

#### 6.3 网络效率设计

- 下行/上行 ≈ 4:1 → 同时从 ~4 个 peer 下载
- Piece 分成 16KB sub-piece → 跨多个 peer 并行下载 → 组装成完整 piece
- 利用多条并行 TCP 连接绕过单连接的性能瓶颈

#### 6.4 Piece 选择算法（4 个阶段）

1. **Strict**：一旦开始下载某个 piece 的 sub-piece，必须先完成这个 piece
2. **Rarest First（最关键）**：
   - 优先下载 swarm 中最稀有的 piece
   - 原因：降低 seeder 压力、提高鲁棒性（万一 seeder 掉线）、加速分发、提升自身价值
   - 最常见的 piece 留到最后
3. **Random Start**：刚加入时什么都没有，随机请求任意 piece 以快速获得可分享的内容
4. **Endgame**：只剩最后一两个 piece 时，向所有 peer 请求，加速变成 seeder

#### 6.5 Peer 选择与 Choking 机制

- 连接到 tracker 分配的 ~10 个 peer
- 实际同时从 4 个 peer 下载（unchoke 4 个）
- 每 **10 秒** 评估各 peer 的上传速率
- 每 **30 秒** "Optimistic Unchoking"：随机选一个被 choke 的 peer 给机会
  - 测量性能 → 和当前 4 个比较 → 保留最好的 4 个
  - 给所有人公平机会，减少 free-rider 影响

#### 6.6 Seeder 阶段

- 下载完成后进入纯上传阶段
- 不再看自己的下载速率，而是看向其他 peer 的上传速率
- 目标：尽快帮助更多 leecher 变成 seeder
- 优先服务带宽好的 peer → 优化整体分发效率

> **录播补充（学生提问）**：有些 BT 客户端支持跨文件积分——你在其他下载任务中的贡献可以给你在当前任务中加分。关于身份欺骗：BT ID 是随机 160bit 数字（没意义去伪造），IP 地址必须真实（否则别人无法连接你），投毒需要让所有 SHA-1 校验通过（非常困难）。

### 7. Distributed Hash Table（DHT）

#### 7.1 动机

Tracker 是单点故障。2005 年 Bram Cohen 提出 Trackerless BitTorrent，使用 DHT 替代 Tracker。

#### 7.2 核心思想

- 将 Tracker 数据库分布到所有 peer 上
- 每个 peer 可以是一个 tracker 节点
- 节点之间组成覆盖网络（overlay network），用于共享元数据（不是文件本身）
- 每个节点只需要知道部分其他节点

#### 7.3 DHT 要求

- 自治、去中心化、容错、可扩展
- 查询解析使用最少的消息数
- 能应对 churn（节点频繁加入/离开）

#### 7.4 数据分配机制

每个 piece 有一个 KeyID，每个节点有一个 NodeID（相同数值空间，BT 中为 160 bit）。

**分配规则**：KeyID 分配给其最近的后继 NodeID。

示例（ID 空间 [1, 150]，3 个节点 NodeID = 40, 90, 140）：

- KeyID 45 → NodeID 90（40 < 45 ≤ 90）
- KeyID 111 → NodeID 140（90 < 111 ≤ 140）
- KeyID 149 → NodeID 40（wrap around：140 < 149，超过最大节点 → 回到第一个）

#### 7.5 环形拓扑

将 ID 空间组织成环（ring）：

- 节点按 NodeID 排列在环上
- 每个节点负责从前驱到自己之间的所有 KeyID
- 初始时每个节点只知道自己的前驱和后继

#### 7.6 查询解析

- **简单方式**：沿着环逐跳转发 → O(N) 步，O(2) 个邻居
- **优化方式**：每个节点额外记住一些"快捷节点"（通常按指数分布）→ O(log N) 步，O(log N) 个邻居

> **录播补充**：如果有 16 个节点，可以让每个节点知道距离自己 1, 2, 4, 8 跳远的节点（指数间隔），这样任何查询最多 log₂(16) = 4 步就能到达目标。

#### 7.7 存储冗余

Key/Value 不只存在负责节点上，还会复制到前驱和后继节点，确保某个节点掉线时数据不丢失。

#### 7.8 Churn 处理

- **节点正常离开**：通知前驱和后继邻居，移交数据
- **节点崩溃**：通过 ping 超时检测，邻居接管其数据
- **新节点加入**：找到一个 boot peer → 计算自己在环上的位置 → 从邻居获取应负责的数据

#### 7.9 DHT 的局限和应用

**局限**：只支持精确查找（lookup），不支持模糊/通配符查询（哈希后的正则表达式没有意义）。

**已扩展到的应用：**

- 文件系统、数据库、域名系统（类 DNS）、CDN
- 通信/消息系统、事件通知
- 应用层多播、PubSub 框架
- 电子健康记录

> **录播补充**：Markus 还提到有人研究了二维甚至更高维度的 DHT 拓扑（球面、环面、5 维超立方体），以适应特定的网络地理分布（如澳大利亚和日本的集群），但这些在 PPT 上很难画所以只讲了一维环。
