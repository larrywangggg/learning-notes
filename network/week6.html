Part 1 — HTTP 与 Web（T5b）

1. 传输协议选择基础

Slide 2

这是贯穿整个 Topic 的核心前提：应用层自己选择传输协议，没有强制规定必须用 TCP 或 UDP，甚至可以自己写一个传输协议（前提是能让路由器放行、不被当成 DDoS）。

场景选 TCP选 UDP
数据量大量内容传输短消息、单次查询
会话长时间、复杂会话轻量、一问一答
可靠性必须保证丢了再问一次（ARQ 够用）
服务端状态需要维护连接状态服务端几乎无状态
协议设计负担高 — 字节流，必须自己定义命令边界低
核心概念
TCP 是字节流（bytestream），没有消息边界。应用层必须自己定义：命令从哪里开始、到哪里结束。这是设计应用层协议时最基础的工程问题。HTTP 用空行 \n\n 作为命令终止符就是这个原则的体现。

2. Web 历史与起源

Slide 3

互联网早期的问题

  • 所有内容本地运行，想要什么就下载到本地
  • 发现内容靠：杂志、新闻组、邮件列表，别人告诉你的是 IP 地址，不是域名
  • 内容发现（Discovery）是根本性难题

前驱协议（Archie / Gopher / WAIS）— 重要考点

  • Archie：面向档案库/仓库的搜索工具（Archive → Archie）
  • Gopher：内容页面链接式浏览，美国俚语"go for something"
  • WAIS（Wide Area Information Service）：委员会/标准组织设计，规格书厚达数英寸且需要付费购买，没有免费服务器实现 → 根本没人用
Lecture 吐槽要记住
WAIS 是"委员会设计 vs 学术开源"的反面教材：Archie 和 Gopher 由学术人员开发、开源发布；WAIS 由标准机构开发、收费买规格 → 结局：WAIS 死了，Archie/Gopher 也没活多久，但 Web 赢了。

Tim Berners-Lee 与 WWW

  • CERN（法瑞边境高能物理研究所）的 IT 经理，1989 年
  • 日常被人问：这个文档在哪？那个数据集怎么拿？→ 想自动化这件事
  • 核心思想来源于 超文本（Hypertext）：文本中可以嵌入指向其他内容的链接
  • 发明了 HTML（标记语言）+ HTTP（传输协议）
  • 第一个 URL：http://info.cern.ch/hypertext/WWW/TheProject.html（CERN 曾关闭该服务器，公众强烈反对后恢复，现在仍可访问）
  • 现在领导 W3C（管 HTML/XML 标准），HTTP 归 IETF 管

3. HTTP 版本演进

Slide 4
版本时间关键变化
HTTP/0.91989Tim 内部测试版，只有 GET
HTTP/1.0RFC 1945正式版，端口 80，TCP，文本协议，每资源一连接
HTTP/1.1~1997持久连接、流水线，沿用至今（约 30 年）
SPDY~2010Google 实验，未广泛采用
HTTP/2.0~2015请求优先级、Header 压缩、Server Push（有争议）
HTTP/3.0RFC 2021基于 QUIC/UDP，内置安全，消除 TCP 队头阻塞
版本协商机制
每个请求都带版本号（如 GET / HTTP/1.0），服务端返回响应时也带自己支持的版本（如 HTTP/1.1），相当于在暗示"我支持更高版本"。所有服务端向后兼容 → 自动协商最高公共版本。

4. URL 结构详解

Slides 5–7 
scheme://user:password@host:port/path?query#fragment

Scheme（协议头）

IANA 维护注册列表，目前约 280 个。常见的：

Scheme用途注意点
http:// / https://Web默认端口 80 / 443
callto:// / tel://拨打电话手机上点击直接触发拨号
mailto://发邮件可预填 subject / body
file://本地文件PowerPoint 不识别（太 OS-specific）
ftp://文件传输粗暴：只能拿整个文件

User:Password（内嵌认证）

安全警告 — 考点
用户名密码以明文写在 URL 里。即使套 HTTPS 加密了连接，这串文字本身还是写在页面上的。绝对不该这样做。

Host & Port

  • Host：DNS 可解析的名字或 IP 地址
  • Port 不写默认 80；如果不是 80，必须显式写出
  • Host Header 的妙用：同一个 IP 上可以跑多个虚拟主机（Virtual Hosts），服务端靠 HTTP 请求里的 Host Header 来区分"你要的是 ANU 的网站还是学院的网站"

Path

  • 可以是文件系统里的真实路径
  • 也可以触发服务端一个程序（如数据库查询）
  • 服务端不需要告诉客户端"这是文件"还是"这是程序生成的"，输出格式对就行

#Fragment（锚点）

跳转到页面内某个特定位置，例如 http://en.wikipedia.org/wiki/IEEE_802#See_also。这部分不会发给服务端，浏览器本地处理。

?Query（查询参数）

  • 传参给服务端程序，用 & 连接多个参数
  • 你在 URL 里看到的那串乱码，很多时候是追踪 Token，不是功能参数
Lecture 具体例子
Telnet 到 Google.com:80 发 GET 请求，收到 302 重定向，Location 指向 google.com.au，同时附带 ?gfe_rd=cr&dcr=0&ei=xxx。这些 query 参数是追踪 token，让澳洲服务器知道"你是从美国那台机器过来的"，之后所有搜索结果都可追踪。

5. 静态 vs 动态内容

Slide 8

静态内容

服务端直接返回文件，内容固定。

服务端动态（早期：CGI）

  • CGI = Common Gateway Interface：客户端发请求，服务端运行一个程序，把输出当作 HTTP 响应返回
  • 缺点：100 万个客户端同时发请求 → 服务端 CPU 炸

客户端动态（现代主流）

  • 服务端把数据（可能比需要的多）推给客户端
  • 客户端 JS 本地渲染、处理、交互
  • 服务端卸载 CPU 压力

两者结合（实际情况）

Google Maps 的例子：

  • 瓦片图（Tiles）：按视口范围预取周围一圈，拖动时边缘触发自动预取
  • 路网 Overlay：另一层数据
  • 实时交通 Overlay：再一层，持续更新
  • 三层数据独立传输、独立刷新，全部跑在同一个 HTTP 连接上
关键点
客户端（浏览器）完全不知道收到的是静态文件还是程序动态生成的，只要格式正确就渲染。这是 Web 架构最核心的灵活性来源。

6. HTTP 完整 8 步流程

Slide 9
  1. 解析 URL — 拆出 scheme / host / port / path / query / fragment
  2. DNS 解析 — 把 host 转成 IP 地址
  3. 建立 TCP 连接 — 三次握手到 IP:Port
  4. 发 HTTP 请求 — Method + Path + 版本 + Headers
  5. 接收内容 — 响应头 + body
  6. 关闭 TCP 连接（HTTP/1.0 的行为）
  7. 解包内容 — 解压缩、解码等
  8. 渲染 — 浏览器渲染 HTML，触发更多 GET
HTTP/1.0 的性能问题就藏在这里
一个网页有 100+ 资源，HTTP/1.0 对每个资源重复做 3~6 步 → 大量时间浪费在 TCP 握手/挥手上。

7. HTTP 请求方法

Slide 10
方法语义实际状态
GET获取资源最常用
HEAD只获取 Headers，不要 body用于缓存检查，节省带宽
POST提交数据，追加到资源用于表单提交、交互式网站
PUT在服务端创建/替换文件基本废弃——允许远程写服务器文件，风险极大
DELETE删除资源基本废弃
LINK / UNLINK建立/断开资源链接已废弃
HEAD 方法的重要性
不需要下载整个文件就能知道它"上次修改时间"、"文件大小是否变化"——这是缓存验证的核心机制。比下载整个 1MB 图片再对比要高效得多。

8. HTTP 响应状态码

Slide 11
范围类别典型例子
1xx信息基本不用
2xx成功200 OK；201 Created
3xx重定向301 Moved Permanently；302 Found/Moved Temporarily
4xx客户端错误400 Bad Request；403 Forbidden；404 Not Found
5xx服务端错误500 Internal Server Error；503 Service Unavailable

301 vs 302 — 重要区别

  • 301 Moved Permanently：永久移走了。客户端应该更新书签，以后不要再来这个地址
  • 302 Moved Temporarily / Found：暂时移走了，但每次还是来这个地址，我告诉你临时在哪里
考点 — 状态码文字不标准
状态码的文字描述（reason phrase）没有标准化。Google 返回 "302 Found" 而不是 "302 Moved Temporarily"，但没关系，三位数字才是权威，文字只是参考。

实用区别（Transcript 补充）

  • 看到 4xx：你的问题，需要修 URL 或者认证
  • 看到 5xx：服务端的问题，不是你的锅，等一会儿再试
  • 503 Service Unavailable：服务端某个后端进程挂了

9. Telnet 实验解读

Slides 12–13

Telnet 本来是远程登录协议，但因为 HTTP 是纯文本协议，可以用 Telnet 手工发 HTTP 请求来观察协议行为。

telnet www.google.com 80
GET / HTTP/1.0\n\n

注意：请求末尾必须有两个换行（一个空行），这是 HTTP 命令的终止符。

正常响应（302）

  • 返回 HTTP/1.0 302 Found（注意：Google 用 "Found" 不是 "Moved Temporarily"）
  • 包含 Cache-Control: private、Content-Type: text/html; charset=UTF-8
  • Location: http://www.google.com.au/... — 重定向到澳洲版
  • Body 是一段 HTML，说明重定向目标

错误响应（400）

GET / HTTP/4.0\n\n
  • HTTP/4.0 不存在 → 服务端返回 400 Bad Request
  • 说明版本号校验是协议内置的，不是可选的

CommBank 的例子（Transcript 独家）

Telnet 到 commbank.com.au:80 → 立即收到重定向，要求切换到 HTTPS（443 端口）。这是银行网站强制 HTTPS 的标准操作。

11. HTTP 无状态与 Cookie

Slide 15
核心概念
HTTP 是无状态协议（Stateless）：每个请求完全独立，服务端不为你保存任何状态。TCP 连接可能几小时前就断了，你再发新请求时服务端不认识你。

维持会话的两种方式

  1. URL 中嵌 Session Token — URL 后面那串乱码，包含时间戳（如"一小时后过期"）
  2. Cookie — Netscape 浏览器提出，由服务端写入，客户端存储，相关域请求时自动携带

Cookie 类型详解

类型特征
Session Cookie关闭浏览器/标签页即删除
Persistent Cookie有 Expiry 字段，到期前一直保留
Secure Cookie仅通过 HTTPS 传输
Third-party Cookie第三方网站写入的 Cookie（追踪核心）

第三方 Cookie 追踪机制（Transcript 详细讲解）

  1. 你访问 ANU 首页，页面底部有 Facebook 的图标
  2. 这个图标不存在 ANU 服务器上，是 Facebook 服务器的资源 → 你的浏览器要去 Facebook 请求它
  3. Facebook 返回图标，同时给你种一个 Cookie
  4. 你访问堪培拉时报，同样有 Facebook 图标，浏览器再次请求，带上了刚才的 Cookie
  5. Facebook 现在知道：这个用户同时访问了 ANU 和堪培拉时报
  6. 积累足够多的网站后，Facebook 对你的浏览行为了如指掌
1×1 像素透明图片的手段
某些网站在页面里放一个 1×1 白色透明图片，来自第三方服务器。你看不见它，但你的浏览器为了渲染页面必须去请求它 → 第三方服务器趁机给你种 Cookie，完成追踪。

Transcript 建议：去浏览器看 Cookie 列表，正常浏览一周后可能有数千个。

12. 协议性能问题

Slides 16–17

为什么性能重要

  • 网页加载时间慢 1 秒 → 用户去竞争对手那里买东西
  • 现代网页 100+ 个独立资源：HTML、JS、CSS、字体、图片、子框架……
  • 实际内容（HTML 文字）只占全部数据的很小比例（ANU 首页 HTML 是蓝色小块，图片是紫色大块）

性能瓶颈来源

  • 浏览器、服务端本身的处理能力
  • 内容结构和复杂度
  • HTTP 协议本身（连接管理）
  • TCP 协议行为（拥塞控制，Topic 7 专讲）
  • 网络路径、带宽、RTT

三条改进思路

  1. 根据客户端能力调整内容（小屏给小图）
  2. 缓存——避免重复下载
  3. 改进 HTTP 连接管理方式

13. 持久连接、流水线与并行请求

Slides 18–21

HTTP/1.0 — 原始模式（慢）

  • 每个资源：TCP 建立 → HTTP GET → 下载 → TCP 关闭
  • 每次 TCP 握手/挥手都是纯浪费时间
  • 信道实际传输数据的时间占比极小（大部分时间在握手和等待）
  • 资源越多越糟糕

方案一：并行请求（Parallelism）

  • 同时开 8+ 个 TCP 连接，并行 GET
  • 优点：服务端无需改动
  • 缺点：突发 CPU/NIC 负载；突发流量 → 增加丢包概率；8× 资源消耗（两端）；ANU 首页 100 资源 → 开 100 个连接？

方案二：持久连接（Persistent Connection）— HTTP/1.1

  • 开一条 TCP 连接，顺序请求多个资源，用完再关
  • 消除了反复握手/挥手的开销
  • 仍然是顺序的：必须等上一个响应完才能发下一个请求

方案三：流水线（Pipelining）— HTTP/1.1

  • 边下载 HTML，边解析，发现需要图片就立刻发 GET 请求，不等前一个完成
  • 服务端按顺序处理请求，按顺序返回响应
  • 问题一：队头阻塞（Head-of-Line Blocking） — 某个资源慢（数据库查询、损坏的磁盘），后面所有资源都等着
  • 问题二：TCP 拥塞控制的影响（Topic 7 细讲）
现代浏览器的实际做法
混合使用三种方式：持久连接 + 流水线 + 有限度的并行。某个资源超时就触发重试。没有哪种单一方案是完美的。

Slides 对比图（Slide 21）解读

  • 黄色 = TCP 建立；绿色 = HTTP 请求；蓝色 = 数据传输；红色 = TCP 关闭
  • Original：每次都有完整的黄-绿-蓝-红循环，大量空白（空闲）时间
  • Persistent：去掉了中间重复的黄红，总时间明显缩短
  • Persistent + Pipeline：请求提前发出，蓝色块更紧凑，但仍受 TCP 和 HOL 制约

15. 缓存机制

Slides 24 / 28

浏览器本地缓存

  • 去过的网站大概率还会去，浏览器乐观地保存所有内容
  • 需要验证资源是否已改变，不能盲目用旧版本
  • 浏览器会追踪哪些网站访问频率高，优先保留它们的缓存

缓存验证机制（HTTP 内置）

机制HTTP 版本工作方式
Expires1.0服务端告诉你"到这个日期之前都可以用缓存"
Last-Modified1.0上次修改时间；客户端可用 If-Modified-Since 条件 GET 验证
ETag1.1类似内容指纹/校验和；客户端用 If-None-Match 验证
HEAD 请求1.0只拿 Headers 不拿 body，用于快速验证是否变化

Partial GET（HTTP/1.1）

  • Range Header：只请求资源的某一段字节
  • 最典型用途：视频播放器请求特定时间段的视频帧，YouTube 的"灰色进度条"预取就靠这个
缓存设计的初衷
Tim Berners-Lee 在 1989 年设计 HTTP 时就把缓存机制内置进去了——这不是后来加的补丁，而是协议的核心设计。

16. 代理（Proxy）与缓存代理

Slides 25–27

代理的基本概念

代理在 Client 和 Server 之间，代替 Client 做工作。对 Client 来说代理像服务端，对 Server 来说代理像客户端——把一个 TCP 连接劈成两段。

缓存代理（Caching Proxy）的收益

受益方具体收益
客户端更近的缓存 → 更低延迟
网络/ISP出口带宽使用减少（内容在校园/企业内部命中）
服务端请求量减少，负载降低
组织安全可在此做安全扫描（检查文件类型、可执行内容）
访问控制组织可在此执行访问策略（屏蔽特定内容类型）

缓存代理的局限（Downsides）

  • 加密流量（HTTPS）无法读取内容 → 无法缓存
  • 动态内容（URL 相同但结果不同的数据库查询）无法缓存
  • 单次访问的"垃圾"内容占据缓存空间（一个学生查了一次没人再查的东西）
  • VPN 流量绕过代理

代理的 HTTP 扩展头

  • Proxy-Authenticate：代理认证
  • Forwarded：转发信息（原始客户端 IP）
  • Proxy-Connection：代理连接控制

客户端如何知道用哪个代理

  • 浏览器手动配置代理地址
  • 自动代理发现（PAC 文件）
  • 网络管理员做深度包检测（Deep Packet Inspection）：检查每个 TCP 流的 HTTP payload，透明拦截 → 成本极高但确实有人做
安全陷阱
如果你以为用 HTTPS 连接了代理，而代理对外是明文 HTTP，你以为安全其实不安全。代理把你的加密流量剥开再转发了。

17. CDN（内容分发网络）

Slide 29

与代理缓存的区别

  • 代理缓存：被动，等客户端请求了才填充
  • CDN：主动，在请求到来之前就把内容推到全球各地的缓存节点

CDN 工作机制

  1. 内容提供商（如 CNN）与 CDN 签约
  2. CDN 在全球部署缓存节点，内容提前推送过去
  3. DNS 配置：用户查询 cnn.com → DNS 返回最近的缓存节点 IP
  4. HTML 中的资源链接也指向缓存节点（不是源服务器）

Akamai 的故事（Transcript 详讲）

  • 1995-1996 年成立，HTTP/1.0 时代就看到了这个机会
  • 全球数百个 PoP（节点），看到大量全球 Web 流量
  • 对网络行为、攻击模式有极深的洞察力
  • 至今仍是极度富有且有效的商业公司
Win:Win:Win
用户赢（更快）、内容提供商赢（服务器压力小）、ISP 赢（骨干网流量减少）。三方都受益，这也是 CDN 能成功的根本原因。

18. HTTP 2.0 / 3.0 / QUIC

Slides 30–32

HTTP/2.0

  • 客户端可以给服务端请求设置优先级（先发 HTML/CSS，图片后面再说）
  • Header 压缩（HPACK）
  • Server Push：服务端预测你接下来要什么就主动发过来（"你要首页，你肯定还要这个 logo"）
  • Server Push 争议很大，实现复杂，HTTP/2.1 至今没出来
  • Apache 等服务端在实现 HTTP/2 时加了一些额外的优化但比较混乱

HTTP/3 / QUIC

重点考区
HTTP/3 基于 QUIC，QUIC 基于 UDP，但加了部分 TCP 功能。根本目的是消除 TCP 的队头阻塞，并减少连接建立的 RTT 次数。
特性说明
基础协议UDP（Quick UDP Internet Connections）
可靠性在 UDP 层自己实现：序列号、校验和（类似 TCP 但更灵活）
安全内置 TLS，连接建立时一并完成，从 7 个 RTT 降到 2 个
队头阻塞每个流独立，一个流的丢包不阻塞其他流
兼容性部分 ISP 限速 UDP → 自动 fallback 到 TCP
标准化RFC 8999-9002（2021）

QUIC 的研发历史（Transcript 独家）

  • Google 约 2011-2012 年开始研发
  • 2013-2014 年就悄悄部署到 Chrome 和 Google 服务器——全球用户在不知情的情况下成了实验对象
  • 研究人员用 Wireshark 抓包才发现"这是什么协议？"
  • IETF 不满这种开发方式，但最终接受并推进标准化
  • 现在约 1/3 的 HTTP 流量跑在 QUIC 上

谁在用 HTTP/3

  • 浏览器：Chrome、Edge（Chromium）、Firefox、Safari、Opera
  • 移动：Android 原生库、iOS
  • 服务端：NGINX、LiteSpeed、MS IIS ✓ — Apache：还没有
  • 商业：Google、Facebook、Instagram、Uber
  • 检测工具：http3check.net

19. HTTP 被滥用为"传输协议"

Slide 33
  • HTTP 开始承载实时音视频（本该用 RTP 的场景）
  • SOAP、REST、AJAX — 机器对机器的 RPC（远程过程调用）跑在 HTTP 上
  • 被用于防火墙穿透：什么都被防火墙拦，但 CEO 要上网 → 80/443 端口不能封 → 所有人都把东西塞进 HTTP

Part 2 — 实时通信（T5c）

1. 实时流量面临的挑战

Slides 3–4

什么应用需要"实时"

  • 音视频：电话、视频会议（双向交互）
  • 远程手术 / 远程医疗（telesurgery）
  • 机器人控制、工业控制（阀门、信号、铁路道岔）
  • VR / AR：手机移动速度快，overlay 必须实时对齐，高 latency 导致不对齐
核心 Trade-off — 贯穿全章
时效性（低延迟） vs 可靠性（不丢包） — 两者不可兼得。可靠性靠重传，重传需要时间。你必须为你的应用选择一个平衡点。

实时通信的复杂度

N 个站点的视频会议：复杂度是 O(N²)——每对站点之间都需要维护连接和同步。

Transcript 中的极端案例

  • 音乐远程协奏：舞台在欧洲 + 大提琴手在阿根廷 + 舞蹈演员在泰国，实时合演。音乐家的大脑自适应了延迟，提前按节拍演奏
  • 夏威夷医生在泰国做手术：发指令"刀往前"，然后"停"——如果"停"这条消息丢失，后果灾难性

2. 实时性要求与应用差异

Slide 5
应用类型传输方向推荐协议延迟容忍
视频流媒体（YouTube）单向TCP / HTTP可以有几秒缓冲
视频会议（Zoom）双向交互UDP极低，150ms 以内较理想
机器人控制双向UDP（或专用网络）极低，且需要高可靠

人类感知的特性（Transcript）

  • 视频：可以容忍 90% 丢包，大脑能补偿画面模糊/冻结
  • 音频：丢失 10% 就基本不可用
  • 音视频唇音同步：如果音画延迟不一致，比单纯延迟更令人难受
  • 国际卫星电话的案例：澳洲到欧洲约 2 秒延迟，对话变成"轮流独白"而不是对话

3. 网络延迟的构成

Slides 6–9
互联网是 Best-Effort
互联网不保证任何东西，除非你有专用电路。路由器、路径、带宽——都不属于你，你无法控制。

延迟的几个分量

分量说明可控？
传播延迟（Latency）光速限制，纯物理不可控，不可逾越
排队延迟（Queuing Delay）路由器队列等待不可控（路由器不属于你）
抖动（Jitter / PDV）延迟的随机变化量接收端可通过缓冲区应对

理想 vs 现实（Slides 8–9 图解）

理想：所有包以恒定延迟到达（像电路交换，延迟分布图是一根尖峰）

现实：

  • 有些包走了最快路径，到达早（左边的尾巴）
  • 大多数包在"典型延迟"附近到达（分布的峰值）
  • 有些包被重路由、拥塞、分片，到达很晚（右边的尾巴）
  • "典型延迟"比物理延迟高，这个峰值周围的扩散就是 Jitter

发送端 vs 接收端的时间对比（Slides 11–12）

  • 发送端：1、2、3、4、5 号包按时钟均匀发出
  • 接收端：1 号按时到，2 号晚了一点，3 号比 2 号快，4 号极晚，5 号正常……
  • 而且到达顺序可能打乱：1、3、2、5、4
  • 接收端必须处理乱序和延迟这两个问题

4. Jitter（包延迟变化）实测

Slide 10
  • 典型 Jitter 约 15-17ms，不会低于 15ms（Slide 10 中的 UDP 流量测量图）
  • 15ms ≈ 60fps 视频的一帧时长（1/60s ≈ 16.7ms）
  • 偶发峰值可以超过 30ms — 相当于 2 帧的不确定性
  • Jitter 本身也会随时间变化，不是静态的
为什么 Jitter 比延迟本身更麻烦
固定延迟可以通过预先缓冲来补偿（等够了再播）。但 Jitter 是随机的，你不知道下一个包会晚多少 → 缓冲区设多大才够？这是实时通信最核心的设计问题。

5. 接收端缓冲区机制

Slides 13–15

为什么需要缓冲区

  • 发送端：以固定速率发出音视频样本
  • 接收端：同样需要以固定速率播出
  • 网络引入了随机延迟和乱序 → 需要缓冲区来"整平"

缓冲区工作原理

  • Receive Buffer：收包、重排序
  • Playout Buffer：按正确顺序排好，定时播出
  • 缓冲区大小以字节衡量，但实质上是"时间窗口"

最大可接受延迟（Slide 15）

设定一个阈值：超过这个时间还没收到的包 → 当作"丢失"处理，不再等待。这个阈值就是你的 Receive Buffer 大小（时间维度）。

例如 Slide 14：包 4 在最后一刻收到，已经超出了 playout buffer 的时间窗口 → 应用层认为它"丢了"（即使物理上收到了）。

6. 缓冲区大小的 Trade-off

Slide 16
大缓冲区小缓冲区
Jitter 容忍度高（等得起）低（等不起）
端到端延迟高（等满再播）低（接近实时）
丢包率低（超时包少）高（超时包多）
适合场景单向流媒体、录播视频会议、实时控制
设计原则
缓冲区越小，实时性越好，但越容易"卡顿"（glitch）。视频可以接受偶尔卡顿，音频几乎不能接受。每个应用自己权衡，没有统一答案。

7. 修复丢包的手段

Slides 17 / 20

重传（Retransmission）— 基本不用

  • 检测到丢包 → 向发送端请求重发
  • 代价：来回 RTT + 处理时间 + 再次排队延迟
  • 意味着 Receive Buffer 必须极大（等重传包进来）
  • 发送端还得缓冲已发的数据（万一要重发）
  • 例外：IP Multicast 场景下可以向"最近的邻居"请求重传（见下节）

前向纠错（FEC，Forward Error Correction）

  • 发送端在数据中加入冗余信息
  • 接收端即使收到的包有错误/丢失，可以自行重建
  • 适用于：控制信号可靠性、重传代价太高的场景（如深空探测器）
  • 也叫"Adaptive FEC"——根据网络状况动态调整冗余量

编解码器自适应（Codec Adaptation）

  • 丢包率高 → 降低码率/分辨率，减少发送量
  • 需要反向信道（接收端告知发送端网络状况）
  • YouTube 自动从 1080p 切到 360p 就是这个

并行传输（Parallel Transmission）

  • 发第 N 帧时，附带上第 N-1 帧的压缩低质量副本
  • 如果 N-1 帧丢了，N 帧里有它的备份
  • 代价：带宽增加；收益：丢包时有低质量版本填空
  • 也适用于控制信号可靠性（Slide 20 图示：4 3 2 1 并行发送）

错误补偿（Interpolation）

  • 帧与帧之间做插值，丢失的帧用相邻帧近似
  • 类似渐进式图像压缩的思路

8. IP Multicast

Slide 18
  • 发送端发一份，网络在分叉点自动复制给多个接收端
  • 所有接收端也可以是发送端（Everyone is a listener AND a sender）
  • 丢包修复：接收端不必向源发送端请求重传，可以向最近的邻居请求（谁有这个包谁发）
  • 大幅减少重传延迟（邻居比源更近）
  • 用于大规模分发（企业内网视频广播等）

9. 弹性缓冲区

Slide 19

工作原理

  • 监控丢包率：正常 1/100 → 突然变成 4/100 → 网络变差
  • 扩大缓冲区：多等一会儿，给包更多时间到达
  • 播放速度减慢（Slow down playout）：用户看到视频慢了一点点
  • 网络恢复后：缩小缓冲区，播放速度加快（Play fast to catch up）
Zoom/Teams 卡顿的真相
你有时看到某人突然"慢动作"，然后又"加速"一下追回来——就是弹性缓冲区在扩张/收缩。扩张时放慢播放，收缩时快进追赶，通常持续 0.5~1 秒。

10. RTP — 实时传输协议

Slide 21

基本定位

  • 跑在 UDP 之上（也可跑 TCP）
  • 支持任何媒体编码格式
  • 支持多路媒体流合并（如同一视频会议的音频流 + 视频流）

Header 关键字段

字段作用
Sequence Number包的序列号，用于检测丢包和乱序重排
Timestamp媒体时间戳，用于同步播放（不是网络时间）
SSRC（Synchronisation Source Identifier）标识流的来源，用于唇音同步（把音频和视频对齐）
CSRC（Contributing Source Identifier）标识合成流中各原始来源
Payload Type媒体编码类型（用于选择解码器）
M（Marker bit）重要事件标记（如帧边界）

RTP 的能力

  • 多路音视频流合并，选择语言/字幕
  • 唇音同步（Lip-sync）
  • 也可携带白板、共享文档等非标准媒体
  • 支持实时翻译字幕叠加（Transcript 提到）

11. RTCP — RTP 控制协议

Slide 22

设计目的

发送端需要知道：我的流质量怎么样？应该调整码率、纠错力度、重传策略吗？

核心机制

  • 使用奇数端口（RTP 用偶数端口），带外控制，不干扰媒体流
  • 必须限制 RTCP 带宽占用（不能让控制流吃掉媒体带宽）

主要报告类型

类型内容
Sender Report发送端统计：发了多少包/字节，NTP 时间戳
Receiver Report接收端统计：丢包率、最大序列号、抖动值、RTT
Source Description标识参与者信息
BYE离开会话通知
Heartbeat我还活着，流还在传
Retransmission Request请求重发特定包
RTCP 的价值
发送端收到"你有 0% 丢包"→ 提高视频质量；收到"你有 10% 丢包"→ 降码率或加强 FEC。这是实时自适应的核心反馈回路。

13. SIP — 会话发起协议

Slides 24–25

定位

  • IETF 开放标准（RFC 3261+），不关心媒体传输方式本身
  • 主要用于 VoIP / 企业电话系统（澳洲 NBN 后大量使用）
  • 包括：代理（Proxy）、注册服务器（Registrar）、重定向服务器、边界控制器、网关（接入 PSTN）

协议外观

  • 看起来像 HTTP：命令、响应、状态码（但没有 XYZ 码）
  • 跑在 TCP 和 UDP 上
  • 信令流：INVITE → 180 Ringing → 200 OK → ACK → [RTP media] → BYE → 200 OK

SIP vs H.323

SIPH.323（ITU）
来源IETF / 学术电信标准组织（邮电部系统）
规格书开放免费厚度以英寸计，买规格要几千美元
采用情况广泛（VoIP）仅企业视频会议系统残存
SIP 的尴尬
SIP 是优秀的开放标准，但 Zoom、WhatsApp、Telegram、FaceTime、Teams、Messenger——全部不用 SIP，都是私有协议。商业利益让各平台封闭在自己的生态里。Skype 现在也消失了。

14. 单向流媒体与 RTSP

Slides 26–27

单向流媒体 vs 视频会议

  • 单向：不在乎延迟（几秒的缓冲无所谓），强调流畅可靠
  • 接收端"拉"内容（而不是发送端"推"）
  • 可用 TCP：可靠传输，通过滑动窗口管理播出缓冲
  • 播放进度条：红色 = 已播，灰色 = 已预取，无色 = 未下载
  • 跳到灰色区域：立刻播；跳到无色区域：暂停等待下载

RTSP（Real Time Streaming Protocol）

  • 建立流媒体会话，协商传输参数（可以用 RTP/RTCP 或 HTTP 等）
  • 命令：OPTIONS、DESCRIBE、SETUP、PLAY（含时间范围）、PAUSE……
  • 看起来像 HTTP 和 SIP
  • YouTube/Netflix 没有用 RTSP，用的是私有方案
  • 最常见的实际用途：安防摄像头 — 大多数 IP 摄像头提供 RTSP 接口
实用技巧（Transcript）
安防摄像头的 RTSP 流可以用命令行客户端（如 ffmpeg、VLC）直接访问和录制，可以在视频帧间跳转。

15. DASH / HTTP 流媒体

Slide 28

DASH（Dynamic Adaptive Streaming over HTTP）

  • 在 HTTP 上实现自适应流媒体
  • 用 HEAD 请求了解媒体信息和可用格式
  • 用 GET + Range 下载视频片段填充播放缓冲区
  • 服务端可以根据请求做自适应编码（不同码率/分辨率）
  • HTML5 内置 <video> 标签（Flash 的终结者）

为什么用 HTTP 做流媒体

  • 防火墙穿透：HTTP 端口基本不封
  • 服务端无状态（每个 GET 独立）→ 更容易扩展
  • 天然继承 HTTP 的代理、缓存、CDN 基础设施

YouTube 流量特征（Transcript）

抓包 YouTube 流量可以看到锯齿波（sawtooth pattern）：客户端定期下载几 MB，把缓冲区填满，然后暂停等播放消耗，再重新下载。这就是 DASH 的节奏。

"唉，还是用 HTTP 吧"（Slide 28 标题）
RTSP/RTP 是更专业的流媒体协议，但 YouTube 和 Netflix 选了 HTTP/DASH，原因直白：防火墙、现成基础设施、开发简单。专业不一定赢，实用才能赢。

"在 best-effort 网络上实现完美、低延迟的实时传输真的很难。所有的智能都在端点，网络本身什么都不保证。"
  • 实时通信的所有优化（弹性缓冲、FEC、codec 自适应）都在接收端/发送端实现
  • 网络只管尽力转发，不保证 QoS（除非你有专用电路：MPLS、RSVP、QoS）
  • 音视频"勉强能用" — 在你的网络条件下
  • 机器人/工业控制用实时流量：互联网可能不是最佳选择，但有时是唯一选择
  • 人脑适应性强（音乐家适应了延迟），机器人不会自适应
