# Database Security Notes

Goal: understand the CIA objectives, access control models (DAC/MAC/RBAC), and common attacks (SQL injection) plus defenses.

---

## 1. Security Objectives (CIA)
- **Confidentiality**: only authorized users can read data
- **Integrity**: only authorized users can modify data correctly
- **Availability**: authorized users can access data when needed

---

## 2. Access Control Models
### 2.1 DAC (Discretionary Access Control)
- Each object has an **owner**
- The owner decides who can access, what they can do, and whether they can re‑grant
- SQL mechanism: `GRANT` / `REVOKE`

**GRANT OPTION / REVOKE key points:**
- You can only re‑grant if you have `WITH GRANT OPTION`
- `REVOKE ... RESTRICT`: deny revocation if others still depend on it
- `REVOKE ... CASCADE`: revoke and remove all dependent grants
- With multiple grant sources, **one remaining source keeps the privilege**

**Examples:**
```sql
-- Alice grants SELECT to Bob, with the ability to re‑grant
GRANT SELECT ON Student TO Bob WITH GRANT OPTION;

-- Bob re‑grants to Carol (only possible with GRANT OPTION)
GRANT SELECT ON Student TO Carol;

-- RESTRICT: fails if Bob has granted to others
REVOKE SELECT ON Student FROM Bob RESTRICT;

-- CASCADE: removes Bob and any downstream grants
REVOKE SELECT ON Student FROM Bob CASCADE;
```

**Multiple grant sources:**
```sql
-- Alice and David both grant to Bob
GRANT SELECT ON Student TO Bob WITH GRANT OPTION;
GRANT SELECT ON Student TO Bob; -- from David

-- Removing one source still leaves the other
REVOKE SELECT ON Student FROM Bob CASCADE;
```

**RESTRICT vs CASCADE intuition:**
- `RESTRICT`: block revocation if it would affect others
- `CASCADE`: revoke and clean up dependent grants

---

### 2.2 MAC (Mandatory Access Control)
- Centrally controlled; users cannot change privileges
- Users have **clearance**, objects have **classification**

**Bell–LaPadula rules (must know):**
- **Read down**: clearance(subject) ≥ class(object)
- **Write up**: clearance(subject) ≤ class(object)

Purpose: prevent high‑level info from leaking to lower levels.

---

### 2.3 RBAC (Role-Based Access Control)
- Permissions are assigned to roles; users gain rights via roles
- Scales well for large organizations

---

## 3. DAC vs MAC (Common Comparison)
| Aspect | DAC | MAC |
| --- | --- | --- |
| Flexibility | High | Low |
| Privilege propagation | Users can re‑grant | System‑controlled |
| Info‑leak protection | Weaker | Stronger |
| Typical attack | Trojan horse | Harder to exploit |

---

## 4. SQL Injection (High Frequency)
Root cause: **concatenating user input into SQL**, mixing control and data.

Common attacks:
- `OR 1=1` authentication bypass
- `UNION SELECT` data exfiltration
- `; DROP TABLE` destructive actions

## 5. Defending Against SQL Injection
**Best solution: parameterized queries**

Principle: **separate control from data**  
The SQL structure is fixed; inputs are bound as parameters.

Example:
```sql
SELECT * FROM users WHERE username = ?
```

Not sufficient alone:
- Blacklists
- Escaping only
- Firewalls/IDS only

---

## One-Sentence Summary
Database security enforces CIA with access control (DAC/MAC/RBAC) and must use parameterized queries to prevent SQL injection in real systems.
