# Harness

Harness 在软件工程语境下有几个常见含义，核心思想都一样：**一个用来"套住"被测对象、让它在受控环境中运行的框架或脚手架。**

## Test Harness（测试工具）

最常见的用法。它是一套自动化测试的基础设施，负责：

1. **搭环境** — 初始化被测模块需要的依赖、mock、fixtures
2. **跑测试** — 按顺序或并行执行测试用例
3. **收结果** — 汇总 pass/fail、覆盖率、日志

Python 里的 `pytest`、`unittest` 本身就是 test harness。当你写 `conftest.py` 配 fixture 时，你就是在搭 harness。

**为什么重要？**

没有 harness，你就只能手动验证代码行为——慢、不可重复、容易漏。有了它：

- **回归测试自动化**：改了代码跑一遍就知道有没有搞坏东西
- **隔离性**：mock 掉数据库、网络，只测你要测的逻辑
- **CI/CD 的基石**：pipeline 里跑的就是 harness，没它就没有持续集成

## ML/AI 语境下的 Harness

在 ML/AI 领域，harness 也指评估框架（比如 `lm-evaluation-harness`），用来在标准 benchmark 上跑模型、对比性能。逻辑一样——受控环境 + 自动化执行 + 结果收集。

---

**一句话总结：Harness = 让你不用人肉验证的自动化骨架。** 没有它，软件质量全靠祈祷。

---

## Agent Harness：别急着换更贵的模型，先把 harness 搞好

这里的 harness 特指 **AI Agent 的执行框架**——围绕在 LLM 调用外面的那层工程基础设施。

**主论点：** 更贵的模型带来的收益远小于预期。真正决定产出质量的是 verification（验证）、boundaries（边界约束）、feedback（反馈循环）、fallbacks（降级策略），而不是模型本身的能力。

**三条实操建议：**

1. **先升级 harness，再考虑换模型。** 如果准确率没动，说明瓶颈不在模型上。
2. **评估是唯一诚实的信号。** 先测你的 harness 够不够好，再去测模型。
3. **小模型 + 强 harness > 大模型 + 弱 harness。** 这条在生产环境中被反复验证。

**关键数据点：**

| 数字 | 含义 |
|------|------|
| 20 行代码 | 就能写一个能跑的 Agent 核心循环——agent 本身不复杂 |
| 4 层 harness | verify（验证输出）、bound（约束行为边界）、feedback（结果回传）、fallback（失败降级） |
| 10× 速度提升 | 来自执行纪律，不是换模型 |

**大白话版本：** 很多团队的做法是"效果不好 → 换 GPT-4o → 换 Claude Opus → 砸钱"，但正确的思路是——先把工程做扎实：校验输出格式、错误重试、边界限制、降级方案。小模型 + 扎实的 harness，一样能打过大模型 + 垃圾架构。

这个观点在业界越来越成为共识，尤其是做过 production agent 的团队体会最深。
